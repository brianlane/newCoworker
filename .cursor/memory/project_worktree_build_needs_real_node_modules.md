In a worktree, a symlinked `node_modules` (pointing at the main checkout) runs
`vitest`, `tsc --noEmit`, and `eslint` fine, but `npm run build` fails with
`TurbopackInternalError: Symlink [project]/node_modules is invalid, it points
out of the filesystem root`. Deleting the symlink and relying on Node's
upward resolution then fails differently: `We couldn't find the Next.js
package (next/package.json) from the project directory`, because Turbopack
refuses to compile files outside the project directory.

So a worktree that needs a production build needs its own real
`node_modules` via `npm ci` (about a gigabyte, a few minutes). CLAUDE.md
offers "symlink the main checkout's, or npm ci" as equivalent options; they
are not equivalent once `next build` is involved.

**Why:** Turbopack resolves the workspace root itself and treats anything
outside the project directory as off limits, for security and performance.

**Second failure mode, seen Aug 5 2026:** the symlink can also be *stale*.
The main checkout's `node_modules` lags its own `package.json` whenever
Dependabot PRs have merged since the last install there, and the worktree
inherits that. It shows up as `tsc --noEmit` errors in files you never
touched: `Cannot find module '@modelcontextprotocol/server'` (a package not
even in `package.json`) and Stripe apiVersion literal mismatches. Nothing is
wrong with the branch; `npm ci` in the worktree cleared all six.

**Third failure mode, seen Aug 13 2026:** no symlink is needed to hit the
staleness trap. Session worktrees under `.claude/worktrees/` sit inside the
main repo path, so Node resolves the main checkout's `node_modules` by plain
upward walking. There it surfaced through ESLINT, not tsc: 9 errors of
"Definition for rule '@next/next/no-location-assign-relative-destination'
was not found" at eslint-disable comments in files outside the diff (the
installed eslint-config-next predated the rule). `npm ci` in the worktree
(15s with a warm npm cache, not minutes) cleared all 9; tsc had been green
the whole time.

**Fourth wrinkle, seen Aug 25 2026:** a session worktree often ALREADY has a
`node_modules/` directory holding only vitest caches (`.vite`, `.cache`,
`.vite-temp`), created the first time you ran the test suite there. So
`ln -s /Users/brianlane/newCoworker/node_modules ./node_modules` does not
fail, it silently creates `node_modules/node_modules`, and the build fails
with the same "couldn't find the Next.js package" message as no symlink at
all. `ls -la node_modules` before assuming the link took. `rm` then refuses
("is a directory"), which is the tell.

**How to apply:** Symlink is fine if the task only needs tests, typecheck,
and lint AND the errors it reports are in files you actually changed. If
`tsc` or `eslint` flags files outside your diff, suspect the stale symlink
before the branch: run `npm ci` and re-run before chasing the error. The
moment the plan includes `npm run build` or running the app (`npm start`,
verifying a page renders), run `npm ci` up front instead of discovering it
after a failed build. Related: [[project-main-run-watch-trap]].
